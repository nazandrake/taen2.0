# Privacy

Taen is an offline keyboard that keeps what you type private. This file lists what is enforced today, how it is checked, and what a keyboard cannot protect
against. The leak audit has its own section below.

## Self-destruct

Settings > Privacy > Self-destruct, behind the app lock. Everything is off until switched on; each trigger is separate.

| Trigger | How it works | False-trigger guard |
|---|---|---|
| Duress PIN | Entered at the app-lock prompt. It must differ from the real PIN (checked when set); the real PIN wins a collision. Both Argon2id hashes are computed on every attempt (a stand-in record when no duress PIN is set; one hash during a wait), so the time tells neither the two PINs apart nor whether a duress PIN exists. It is judged during a wait too (it counts nothing). PINs are handled as character arrays (the pad holds one array that is zeroed) and the hash input bytes are zeroed after use. | Test mode, optional confirmation |
| Trigger word | 12 to 64 characters, no whitespace and no separator the keyboard splits on (. , ; : ! ? / _ brackets and similar, emoji: the typing code would end or change the word before Enter), a digit or symbol, not a dictionary word; entered twice; kept only as salt plus Argon2id (8 MiB x 2, about 240 ms on the reference phone) in the encrypted `selfdestruct` store, nothing else derived from it. Checked only when Enter (and Space, if set) is pressed and the token before the cursor is 12 to 64 characters: one hash, at most the last 65 characters are read. The typed token is a char array that is cleared after the hash; it is never logged or stored. A token for which a check is due never enters the learned words, auto-correction or suggestions, whatever the check finds (rehearsal, cancelled confirmation, Hold Enter off). On a match the word is removed from the field and the key does nothing else. Not checked in password fields (option) and never in the keyboard's own fields. | Length, character class, dictionary exclusion, twice, commit key only, test mode, optional confirmation |
| Wrong PINs | The app-lock counter (stored before each comparison) reaching N (5 to 20). A counter that cannot be decoded counts as exhausted. | Minimum 5, off by default |
| Inactivity | No input session for N days (3 to 365), checked at app start, at the start of an input session and by a daily persisted job (RECEIVE_BOOT_COMPLETED); a missing time starts the clock; a damaged one counts as exhausted; wall-clock time, so a clock set back postpones it (a known gap that needs the unlocked phone). | Minimum 3 days, off by default |
| Panic | Hold for 3 s in settings, or the optional launcher shortcut (off by default), which only opens the question "Clear typing data?". | Confirmation |

Test mode (15 minutes, ends by itself, a far-future end is ignored) makes every trigger show "Trigger recognised (test)" and delete nothing.

What is deleted is configurable (learned words and snippets, clipboard and the system clip, settings and images, imported dictionaries, the lock and these settings; the default is everything). Every kind except possibly the lock and the settings selected: a crypto-shred. The wipe stops every writer, writes a marker (the first thing written), saves the configuration if it stays armed, destroys both Keystore keys (aimed at 200 ms), deletes every file and folder of the data directories (aimed at 2 s), clears the clipboard, writes the kept configuration back under a new key, removes the marker and ends the process (the system starts the keyboard again as new). A partial scope deletes only the selected files and keeps the keys; the screen says so. If the device is locked the keys go at once and the credential-encrypted files are deleted after the next unlock (the marker); a wipe that stopped halfway is finished at the next start (a damaged marker counts as a wipe of everything: both keys are destroyed again and both tiers deleted). Symbolic links are removed, never followed. Checks: `SelfDestructCoreTest`, `TriggerWordTest`, `SelfDestructConfigTest`, `SelfDestructSettingsTest`, `SelfDestructEngineTest`, `AppLockDuressTest`, `WiperTest`, `FileWiperTest`, `SelfDestructWiringTest`, the trigger-word tests in `InputLogicTest`, privacyCheck rules for key deletion and process kill, device scan.

Limits: text already sent to apps, other apps' data, the phone maker's clipboard history and exports saved outside the app are out of reach. A copy of the files taken before the wipe, together with the key blob, may be restorable where the phone lacks rollback protection of the key store. Fragments of a trigger word that is typed are in the learned words until the wipe (learning stays on in normal fields); a String of typed text cannot be wiped from memory on the JVM, so its life is kept short. The setup dialog holds the word in a text field while it is open.

## Not yet enforced

- The blacklist files (`blacklists/*.txt`: main-dictionary words the user removed from suggestions) are still plain text.
- Auto-forget of unused learned words, a data viewer and biometric unlock are not built. The privacy status screen shows the network, backup and accessibility state, not the key security level.
- The old system user dictionary words are not imported (the permission to read them is gone); the personal dictionary starts empty.
- The leak audit is a repeatable suite (section "Leak audit" below); its device part needs a phone over adb and is run before a release.
- The accessibility-data-sensitive marking has no effect on the reference phone (Android 12, API 32); it was checked on the emulator only.
- Debug builds still write fixed log texts to logcat (class names and events, no values); the native engine's own logging is compiled out (FLAG_DBG is off in every variant). A crash prints the exception to the system log as usual; the remaining exception messages in the code hold layout, dictionary-file or setting names, not typed text.

## Leak audit

`make leak-audit` (static, no phone) and `make leak-audit-device` (reference phone over adb) write one report, `build/leak-audit/leak-audit-report.md`
(`BUILDING.md` section 9 lists every check). Every check category has a planted failure that must fail and a clean control that must pass
(`T-*` rows of the report); a check that cannot fail is not counted.

What it proves, and how far:

- Static, on the release APK: permissions equal the allowlist (no INTERNET), backup off with every domain excluded, not debuggable, exported
  components on a reasoned allowlist, no network, tracker, class-loader, log, radio, location, camera, microphone, contacts or account API in the
  dex (the release build strips `android.util.Log`, `PrintStream.print*` and `java.util.logging.Logger.log`; the audit found Compose and AndroidX
  calls to the last two and the build now removes them), native libraries import no socket, DNS, log or console function (the dictionary file
  writers are linked in but their JNI entry points have no caller), 137 runtime dependencies with open-source licences and no tracker group, strict
  checksum verification of every dependency.
- On the phone, with canaries typed in English and Bulgarian, glide, a password field, the clipboard, an export and a wipe: zero bytes of network
  traffic for the Taen UID over the whole session (platform per-UID counters; the process holds no inet group so the kernel refuses sockets; the
  shell UID's own download is the positive control); no canary in logcat (streamed through the session, with a planted control line); no
  plaintext canary in either data directory or the external directories (UTF-8, UTF-16, Windows-1251 and the dictionary encoding; planted file
  control); the encrypted export has the TAENBK1 header and no canary; `bmgr` refuses and `adb backup` yields nothing (release build);
  screenshots and screen recordings are refused or black while the keyboard or the settings screen is shown (a plain white screen is the control);
  sensitive and password-field copies are not kept, paste from the history leaves the system clip alone; the accessibility and overlay warnings fire;
  one tap on the language key switches English and Bulgarian and back; the self-destruct test mode recognises the trigger word and deletes
  nothing, and the real trigger deletes every encrypted store.
- Limits, stated so they are not read as more: no root, so no tcpdump or iptables counters (the per-UID platform counters, process groups and
  `/proc/net` stand in); the data directories can only be read on the audit build (the release code with `debuggable=true`), the release APK itself
  gets the reduced session; `adb backup` archives a debuggable build whatever `allowBackup` says (only public dictionaries were in it), so that
  verdict is taken on the release build; the emoji search view is not driven by the script (emoji suggestions in the strip are); the Pixel 8 Pro and
  Android 14+ behaviour (accessibility-data-sensitive keys) are not tested; the accessibility service sees text typed in normal fields (the
  documented limitation, shown as information row D7i); the first switch to Bulgarian on a new install takes several seconds on the reference phone while the
  dictionary loads (taps are lost meanwhile).
- Fixed finding F1 (row D6b): the keyboard service no longer stores the clip that is on the system clipboard when it starts (it cannot know in which
  field it was copied); `ClipboardServiceStartTest` checks it.

Best-effort lints: two SourceRules checks are text patterns and cannot be a complete boundary (method references are matched, but aliases, wrappers and reflection are not): the provider-I/O rule (provider streams and queries outside FileUtils and the voice model files) and the AppLock main-thread rule. The real guarantees are FileUtils/ProviderJobs as the single owner of documents of other apps (async, size cap, time limit, cancel; FileUtilsTimeoutTest) and AppLock.update's runtime refusal on the main thread (AppLockMainThreadTest). Treat a green rule as a reminder, not as proof.

## Voice typing

Native-code loading gate: SourceRules reject `System.load`, `Runtime.load`, `loadLibrary` outside `JniUtils`, `register*Library` (ONNX Runtime custom-operator and execution-provider libraries) and execution-provider registration (`addExecutionProvider`, `addNnapi`, `addXnnpack`, `addCUDA`, ...) everywhere; leak audit S8 applies the same rule to the release dex (`check_native_loading`; allowed: JniUtils, ONNX Runtime's own two libraries and overloads, AndroidX graphics-path) with planted failures T-S8 and T-S8-load. These are the ways to load code after the build.

Speech is recognised on the phone: ONNX Runtime 1.27.0 (MIT) runs the int8 export of NVIDIA Parakeet TDT 0.6B v3 (CC BY 4.0) on the CPU. Why this
engine: of the open options checked it has the best Bulgarian result (12.6 % WER in the model card, against 37 % for Whisper small) with a real-time
factor far below 1; whisper.cpp would be fully source-built but is not usable for Bulgarian at the sizes a phone runs; Vosk has no Bulgarian model; a
hand-over to another voice input method is outside the invariants and is gone. The model is not in the APK and is never downloaded by the keyboard (the manifest has no

## Cursor navigation

The space bar moves the cursor across characters and, in multi-line fields, up and down lines (one arrow key per key-row height;
a single-line field never gets an up or down key, which could move the focus to another view). Selection, "select next occurrence"
and cursors on several lines work in memory only: the keyboard reads the field text when a key asks for it, keeps only the region
between the first and the last cursor and the undo of the last edit (two minutes, with a SHA-256 digest of the whole field, not its
text, so that any other change of the field ends the undo), and drops all of it when the field changes, the
screen locks or you move the cursor yourself. Nothing of it is stored, logged, copied or learned. In password fields and incognito
fields (`PrivacyPolicy`) these keys do nothing and the field text is not read. An edit is written in one batch only after checking
that the region still holds what it held; a field that gives no text, only part of it, or more than 20 000 characters is not
edited. Checks: `SpaceSwipe2DTest`, `SpaceSelectionTest`, `MultiCursorTest`, `NavigationWiringTest`, SourceRules (the navigation
package has no file, network, clipboard, log or preference class).

## Vim mode

Vim mode is off until you turn it on in Settings > Preferences. Then an Esc key appears on the suggestion strip (and in the
toolbar); it opens the Normal layout, and Visual and Visual Line mode have their own layout. A mode line above the keys shows the mode
and the count and operator typed so far. The keys of these layouts are commands, not typing: nothing they do is learned, suggested,
corrected, added to the recent emoji or checked for the trigger word. Commands that change text read the text of the field (up to 20 000
characters, only when the app shares all of it, which the keyboard checks against the text before and after the cursor) and read it
again just before the change; if it cannot be read, changed meanwhile or
is selected, nothing happens and a short message says so. An edit is one text change: a failed cursor move after it leaves the edited
text (Vim mode stops and says so), and a failed change leaves the field as it was. Vim mode is not available in password fields or while the device is locked.

Vim mode keeps some things so that its commands can use them again: the registers (`"a` to `"z`, `"0` to `"9`, `"-`, the last inserted
text `".`, the last search `"/` and the last command line `":`), the macros (they are registers), the record of the last change that `.`
repeats, the marks of the field, the search pattern, the last substitute and the histories of the command line and of searches. All of it is
kept in memory only, in one holder (`VimMemory`) that nothing else in the package may bypass: it asks the rule below again at every write, so
switching incognito on in the middle of a command, an insert or a recording keeps what follows out (a recording, and the typed text of a change
that `.` would repeat, are dropped at that moment; `VimStoresTest` fills every store through real keys in such a field, and
`VimStoresStructureTest` fails when a store or a writer is added without being named). What is typed in insert mode does not pass through
the layer (the typing keyboard writes it to the field and the layer reads the difference at Esc), so the answer of the rule at Esc says nothing
about the time before: an insert session carries one flag, "capture allowed throughout". It is set when the session starts and cleared by
every event the keyboard reports to the layer (the incognito key; every settings reload where capture is off before or after it, which
carries the privacy decision of the field; a field that starts, is restarted by the app or finishes; the screen lock and a wipe; Vim mode
turned off) and by any key that meets a "no"; it is never set again. A session whose flag was cleared is dropped whole, at Esc, at the end of
a recording and at every write into the holder: not its last inserted text, not the `.` record, not the recording, not the marks (they hold a
copy of the field). `VimTaintTest` runs every kind of insert (`c`, `s`, `i`, `a`, `A`, `I`, `o`, `O`, `R`, a count, Visual and block inserts) through it,
and `VimWiringTest` sends each event along its own path (the toolbar key with the settings listener stopped, a settings reload without the key, an input
restarted, finished, the input view finished, the screen lock, the setting off) and fails when one of the wires is removed. It is never written to disk, never logged and never put on the system clipboard, except through the `"+` and `"*` registers,
which are the system clipboard: `"+y` copies and `"+p` pastes through the same code as the copy key and the paste key (a copy keeps the
sensitive flag of a password field, a paste of a number field takes only what the field accepts). Everything else is filled only where
clipboard history may keep a copy (not in a password field, a field that asks for no personalized learning, an app on your incognito list
or while incognito is on): there a command still does its work, but nothing is remembered and a recording stops. All of it is forgotten
when the screen locks, at a wipe, and whenever Vim mode is off (also after a restored backup or an applied profile); marks also go with
the field, and are dropped when the text was changed by anything but Vim mode. A register, a macro and the command line each hold at most
20 000 characters, a macro at most 2 000 keys, and one command that runs several steps (a macro, a repeat, `:normal`, `:global`, an ex line)
has ONE budget: at most 20 000 keys, 100 000 ex steps (a line, an iteration of `:global`, a command) and 2.5 seconds together. Every search,
pattern and `:substitute` is at most 3 million steps and 0.4 seconds, and no text that any command builds may be longer than 20 000
characters (a count, a register, a replacement or a copy that would make it longer is refused before it is built: `:g/^/%t$` cannot double
the text until memory ends). Executions nested in one another (a macro in a macro, `:normal`, `@:`, `@@`, `.` in a macro, `:global` with
`:normal`) are at most 10 levels deep (a play is one level, every `:normal` run one more), and the text copies that executions two or more
levels deep build add up to at most 2 000 000 characters in one command, counted before each copy is built (a macro that calls itself, or
`:normal @:`, stops at the tenth level: `VimNestingTest` has every form at the limit and one level past it, and `VimStressTest` runs them on the
largest field in a child JVM with a 64 MB heap and a 512 KB stack, where no OutOfMemoryError or StackOverflowError may happen). So nothing a user types or a pattern copied from elsewhere can hang the keyboard or use up its memory; at a limit
the command stops, says so and changes nothing (a play or an ex line runs on a copy that is then dropped). An ex line that Vim mode does not
understand (characters left after the command, an unknown flag or argument, an expression register such as `:put =x`, a range where none is
allowed) is refused with a message and never run in part. `:reg` and `:marks` show their listing in the keyboard's own mode line, never in
a toast or anywhere outside the keyboard window. A Visual block insert that must pad a short line writes the padding and the insert together,
once, when the insert ends.
The command line (`:`, `/`, `?`) is typed on the keyboard's own layout, into the engine only: its text is never put into the field, never
learned or suggested, and a swipe or a tapped suggestion is dropped while it is open. A macro, a repeat or an ex command that changes
the text is run on a copy of the text and written to the field as one text change. `p` and `P` insert like the clipboard paste key (no
learning). Checks: `VimGoldenTest` (21 000 cases whose results come from the real vim), `VimEngineTest`, `VimEngineV2Test`, `VimStoresTest`, `VimStoresStructureTest`, `VimMemoryRulesTest`,
`VimBoundsTest` and `VimLimitsTest` (bounds, privacy, one change per command, ex lines that fail closed), `VimTaintTest`, `VimNestingTest`, `VimStressTest`, `VimRegexTest`, `VimWindowTest`, `VimWiringTest`, `PrivacyPolicyTest`, a check of the
compiled classes of the vim package against an allow list (every class of the package, whatever produced it, Kotlin or Java; it may refer
only to plain Kotlin, its own package, a few value types and collections of Java and two pure text classes: no Android, file, network,
clipboard, log, process, thread, reflection, preference or storage class, however the name is written, and no exception message; a member
that a class of the package inherits is checked against the class it comes from, and `java.lang.Long` is allowed as a type only; a type signature that does not parse completely fails the check), a catch at the
one door into the engine (an exception that a library call inside it throws can carry field text in its message, which the system would write to the log: the
keyboard drops anything the engine throws, an Error from a failing initializer included (only an out-of-memory or stack-overflow error of the VM passes), unread, does not log or keep it, shows one generic message and goes back to typing; `GuardedVimEngineTest`) and the release APK scan (no process is started by anything shipped).

## What a keyboard cannot protect against

Taen sees what you type, so it can protect what it stores and shows, not what other software does with the same text.

- The app you type into receives everything and can store or send it.
- Accessibility services can read the target app's fields and the screen. Taen can only warn, and from Android 14 hide its own keys.
- Content capture, autofill services and clipboard history of the phone maker (for example MIUI) receive text through Android, not through the keyboard.
- Root, a compromised or malicious system, kernel keyloggers, and a computer that is allowed to use adb (screenshots of the target app's window, UI dumps, logcat) bypass the keyboard.
- Hardware keyboards bypass the keyboard. The PIN pad of the lock screen is Android's own view.
- Shoulder-surfing, cameras, and sound or vibration of the keys are outside the keyboard (key sound is off by default).
- A forensic image taken before a wipe may be restored together with its key where the phone lacks rollback protection of the key store (the reference phone probably does).
- Someone who forces you to give up the PIN gets what the PIN protects, and can see that the app was reset.
- Play Protect's "improve harmful app detection" may upload unknown APKs: turn it off.
- `FLAG_SECURE` hides the keyboard window and, on this phone, the whole screen while the keyboard is open. It does not stop another person from photographing the screen, and an app can ignore or remove its own secure flag.

## Optional downloads and offline pictures

### Downloads (P22)

- The keyboard has no network (P1). Settings > Downloads lists the rows of the catalogue `assets/catalog/downloads.tsv` (the same file as `tools/downloads.lock`, kept equal by DownloadCatalogTest). Every address is https on codeberg.org or huggingface.co and pinned to a commit (`/raw/commit/<40 hex>/`, `/resolve/<40 hex>/`); a branch name or `latest` fails the test.
- Download hands the address to the browser (DownloadAccess is the only place that builds the intent; privacyCheck allows `Intent.ACTION_VIEW` only there, in the About links and in the incoming-link handler of SettingsActivity). The user then picks the file with the system picker (Install downloaded). The keyboard cannot see the browser's Downloads folder, so "downloaded" is not a state.
- PinnedInstaller (same steps as the voice model store): pass 1 hashes the picked document without writing (a private photo is never copied), pass 2 copies it into `no_backup/taen-downloads/<id>.part`, reading stops at the pinned size + 1, SHA-256 is computed on the way, and only a file with the pinned size and hash is renamed (atomic move) to its target. A wrong file, a cancel, a stalled provider (60 s without a byte), no space (size + 64 MiB margin), a reader that throws, a refused file or a failed rename each end with no `.part` and the earlier target untouched. One install per staging directory; a second is refused (Busy), it does not wait. This is a second copy of the voice steps, not a shared class: the voice classes were left unchanged on purpose (their tests are the proof).
- Dictionary rows: after the hash matched, the staged file must have a readable dictionary header whose language equals the row's language and must open in the native engine (isValidDictionary), as in the free-form "Add dictionary" dialog. The file becomes `files/dicts/<language>/main_user.dict` (the keyboard prefers it over the dictionary in the APK), the extracted copy `main.dict` is deleted and NEW_DICTIONARY_INTENT_ACTION is sent. Remove deletes that file and the dictionary in the APK is used again. A `main_user.dict` that is not this row's file (a dictionary the user added by hand) is never replaced and never removed by the row.
- Downloaded dictionaries and their staging files are IMPORTED data for the wipe (the presence of a language shows which languages are used). Public data, so they stay plain files; a user dictionary in `files/dicts` was already part of the encrypted export, so a downloaded one is too.

### Next-word model (P23, 2.0.0)

- Two optional downloads in Settings > Downloads, the same pinned browser-and-picker path as the dictionaries (P22): `model-en`, SmolLM2-135M (Hugging Face, Apache-2.0), and `model-bg`, Qwen3-0.6B (Qwen team, Apache-2.0), both as the int8 ONNX files of their onnx-community conversions, pinned by commit, size and SHA-256 in `tools/downloads.lock`. They are installed to `no_backup/taen-models/<id>.onnx` (ModelFiles; public data, plain files, hashed again before the first use in each process: a mismatch is "damaged" and the model is never loaded). Their tokenizer files are in the APK (`assets/nextword`, verbatim, `tools/nextword/tokenizers.lock`, leak audit S11: no model file is in the APK).
- Where it runs: NextWordGate is the one place that decides. The model switch (Downloads page, default on), the suggestion strip shown, next-word predictions on, and PrivacyPolicy's personalized-suggestions decision (so never in a password, incognito, no-learning or app-incognito field, and never while the device is locked) must all hold, and the model of the field's language must be ready. Ready means: installed and verified, at least 5 points better than the dictionary in the first three on the reference text, and passed this phone's one-time speed test. Every model is checked on each phone: the test passes when 95 % of the steps take at most 150 ms (English) or 250 ms (Bulgarian) and the memory the phone reported free before the load (ActivityManager.MemoryInfo) covers what the model added plus 1 GB to spare. When less than the model file plus 1 GB is free, the model is not loaded at all and the result is "not enough memory on this phone". Either failure is said plainly and offers Remove. A result that cannot be read counts as not tested; memory that cannot be read fails the test.
- Before every load (the first prediction of a field, again after each unload) the memory free right now must cover what the model added in this phone's test plus 1 GB; otherwise it is not loaded, the strip keeps the dictionary's predictions and the Downloads page says "not enough memory right now". Memory that cannot be read means no load. Each load (and the speed test) writes `<id>.loading` in the model folder first and removes it when the load returns; a marker that a later process finds means the system ended the keyboard during the load (usually for memory): that model's speed result is removed, it is marked `<id>.crashed` and it is not loaded again until a new speed test passes, so a low-memory kill cannot repeat at every start. A marker that cannot be written means no load.
- What it reads: only the text before the cursor that the keyboard already holds (RichInputConnection's cache; no extra read from the app), when the strip shows predictions (no word being typed). It runs on its own thread (ONNX Runtime 1.27.0, CPU only; OrtNextWord, the second and last ai.onnxruntime user). The dictionary's predictions go on the strip at once; the model's order replaces them only if it is ready within 150 ms and nothing changed in between.
- What it shows: the dictionary's predictions reordered by the model, plus the model's most likely next words that are words of the active dictionaries (and not possibly offensive while those are blocked). It cannot show a word the dictionaries do not have. A word only the model added is never learned when it is picked, and a prediction is never an autocorrection.
- What it keeps: nothing on disk. The tokens of the last window and its attention cache stay in memory to make the next word cheaper; they are dropped when the field changes, the screen locks (the engine is unloaded) and two minutes after the last use (unloaded). The Java copies (token ids, scores) are zeroed after use; ONNX Runtime's native memory cannot be zeroed (as for voice, P20). The nextword package has no file, log, preference, network or learning class (SourceRules).
- Wipe and export: `no_backup/taen-models` (models, speed results and the load markers) is IMPORTED data for the wipe (which languages are in use) and a shred removes it; it is never in the encrypted export (ExportServiceTest), and the speed result lives next to the model so that an import cannot carry one phone's result to another.
- Measured (tools/nextword-eval.sh on the build PC, the 1000 held-out contexts of tools/dict-eval.sh; NextWordBench on the reference phone, 4 threads; the next word among the first three suggestions): English (dictionary of the APK): on the reference phone 12.1 % with the dictionary alone and 40.9 % with the model (28.8 points better), 95 % of the steps within 272 ms (median 240 ms) and 337 MB added; on the build PC 40.7 %, 28 ms. The accuracy passes; the speed does not on the reference phone (272 ms over its 150 ms), so there the speed test fails and the model is not used. On a faster phone it is used once its own test passes. The Downloads page shows these numbers and says that the model needs the speed test on this phone. Bulgarian (downloadable dictionary; 1000 contexts on the build PC): 6.9 % with the dictionary alone and 20.5 % with the model (13.6 points better), so it is offered, gated by the test on each phone; on the reference phone (first 100 contexts) 95 % of the steps took 1403 ms (median 1244 ms), it added 1395 MB, and the phone reported 1570 MB free before the load (MemFree + Cached), less than the 589 MB model file plus 1 GB: on this phone the test does not load it and says "not enough memory".

### Pictures (P24)

- Import uses the picker (`OpenMultipleDocuments`, one document at a time through ProviderJobs: size cap, time limit, cancel). Formats by magic bytes: GIF, PNG, JPEG, WebP. Limits: 8 MiB per picture, 500 pictures, 256 MiB in total, refused before anything is written.
- MetadataStrip copies the image segments byte for byte and drops the rest: JPEG keeps JFIF, Adobe and the coding segments (EXIF, XMP, ICC, IPTC, other application segments, comments and everything after the end marker are dropped); PNG keeps an allow-list of chunks (text, eXIf, iCCP, tIME and unknown chunks are dropped; every kept chunk's CRC is checked); GIF drops comment, plain-text and unknown extensions and keeps only the loop extensions; WebP keeps the image chunks and rewrites the VP8X flags and the RIFF size. A picture that does not parse is refused.
- Storage: `media_<random 64 bit hex>.enc` (AES-GCM, credential-encrypted tier, through Privacy.store) and `media_index.enc` (id, format, size, up to 8 tags of 1-32 lower-case characters; no time, no file name, no source). Search and delete run in memory, the search text is never stored. Locked tier: nothing is listed, read or written. Damaged list (or pictures without a list): "damaged", nothing is shown, only Delete all works. A failed list write removes the new picture again.
- Wipe: `media_*` stores are IMPORTED (an explicit rule in FileWiper, not the else-branch, which would put an unknown store name into SETTINGS); a shred removes them with the keys.
- Export: the pictures are exported only as a whole and only when they total 64 MiB or less and the payload stays within ExportBundle.MAX_TOTAL_BYTES; otherwise the export is made without them and says so. An import with pictures replaces the collection (after the payload was validated: list, sizes, formats, parsing): the new pictures are written next to the old ones under new ids and read back, then the list is replaced in one atomic write (the switch), then the old pictures are removed; a crash before the switch leaves the old collection, after it the new one, and unlisted pictures of an interrupted import are removed by the next one; an export without pictures leaves the live pictures alone. The starter stickers are never in an export.
- Sending: the MEDIA toolbar key (off by default; turn it on under Settings > Toolbar) opens the panel. MediaInserter is the only caller of `commitContent`; the field must announce the type in `EditorInfo.contentMimeTypes`, otherwise the panel says "This field does not accept images" and nothing is sent: no clipboard copy and no share sheet as a fallback. The URI is `content://<applicationId>.mediashare/m/<token>`; the token is 128 random bits kept in memory only, valid for 10 minutes, revoked at screen lock, at a wipe and when the input field changes. MediaShareProvider is the one content provider of the app: exported=false, grantUriPermissions=true; it serves the bytes through `ParcelFileDescriptor.createReliablePipe` (no plaintext file is written), `query` answers `taen.<ext>` and the size only. privacyCheck and leak audit S2 expect exactly this provider and the AndroidX startup provider, both not exported, and grants only on the media provider (planted proof T-S2-provider).
- Starter stickers and GIFs: 38 Microsoft Fluent Emoji (MIT) PNG files (1.3 MB) and 36 animated GIFs from Google's Noto Animated Emoji (CC BY 4.0, scaled to 128 px, 2.1 MB) in the APK (`assets/stickers`, `tools/make-sticker-pack.sh` rebuilds them from `tools/sticker-pack.lock` and `tools/sticker-gifs.lock`; credit in NOTICE). Off until the setting is turned on; tagged `sticker` and `gif` for the tag chips; never stored in the vault, never exported. The GIFs are sent as `image/gif` through MediaInserter like every picture. The app downloads nothing: the files are fetched on the build machine only.
- Animated tiles: a GIF or WebP tile that is on screen is played with the platform decoder (`ImageDecoder` and `AnimatedImageDrawable`, no library) from the decrypted bytes in memory (`ImageDecoder.createSource(ByteBuffer)`, no file, nothing written), decoded at tile size (longest side 160 px) so that a large picture cannot take much memory. The animation stops and is released, and the bytes are zeroed, when the tile scrolls off, the panel closes or the screen locks; still pictures are not animated.
- Residual risks: the receiving app keeps what it was sent (that is the point); a thumbnail is decoded from the decrypted bytes into the Java heap while the panel is open and is dropped when it closes (not zeroed: a Bitmap); the bytes of a playing tile stay in memory while it plays (zeroed when it stops; the platform decoder may keep its own copy until it is released); a receiving app that is slow to read can fail when the token expires after 10 minutes.

### Emoji on a held key and pictures in the emoji panel

- Setting "Open emoji by holding" (`emoji_hold`: comma, period, space, language, none (default: an update keeps every key and its menu as it was); an INCLUDED device-protected key, so profiles and the quick panel carry it; the quick panel has one button that steps through the five). It uses the mechanism the shift key has for its caps-lock hold: the chosen key gets ONE popup key (emoji) behind `!noPanelAutoPopupKey!`, so a long press carries it out at once (PointerTracker.onLongPressed), with the emoji key on the bottom row shown or not. The key's own popup menu is not shown while it holds emoji (the comma key's clipboard, settings and so on; the toolbar has them); "none" brings every menu back. The value is part of KeyboardId, so a change parses the layouts again. Templates: `bulgarian_daily` sets `comma`, `minimal` sets `none`. Number layouts are not changed. No privacy effect: no data, only a key binding.
- The emoji panel has a pictures tab at the end of its tab strip (only where the tab strip is shown). It opens the same panel as the MEDIA toolbar key (MediaPanelView): the user's pictures, the starter stickers when switched on, narrowing by tag chips, the same MediaInserter path and the same "This field does not accept images" message. A category tab leads back to the emoji pages. Search by typed text is in Settings > GIFs and stickers; the panel has no text field of its own (an input method panel cannot take typing).
